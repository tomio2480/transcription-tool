## 🔁 レビュー 3 巡の指摘と共通パターン

表 1. Codex の指摘と対応

| 巡 | 指摘 | 対応 |
|---|---|---|
| 1 | 前回の txt が残ると出力存在確認が無意味 | whisper 起動前に前回の txt を削除 |
| 1 | `exists()` ではディレクトリでも OK になる | `is_file()` で判定 |
| 1 | zip キャッシュ時に展開を永久スキップ | 実体が無ければ再展開 |
| 2 | 入力 WAV が出力先にあると ffmpeg の入出力が同一 | 中間 WAV を `<stem>.16k.wav` に |
| 2 | バリアント切替後に戻すと展開スキップ | `bin/.variant` に記録し不一致で再展開 |
| 2 | data-dir が通常ファイルでも OK | `is_dir()` で判定 |
| 3 | `setup` のディレクトリ作成が `try` の外 | 作成失敗を捕捉し終了コード 1 |
| 3 | ffmpeg 不在が終了コード 1 | 事前検査で環境不備として 2 |

指摘は 4 つのパターンに集約できる．

- **状態の証明**: 存在することは今回生成したことを意味しない．前回の成果物を消してから作る．
- **種別の検査**: `exists()` は種別を見ない．ファイルには `is_file()`，ディレクトリには `is_dir()` を使う．
- **キャッシュと配置の分離**: 取得済み（zip）と配置済み（展開物）は別の状態である．配置の妥当性を独立に確かめる．
- **終了コードの契約**: 環境不備（2）と実行失敗（1）を分ける以上，検出は事前検査で行う．実行中の例外変換に頼らない．

レビューは 1 巡ごとに P1 1 件 → P2 3 件 → P2 2 件と収束した．
同じ観点の指摘は，巡をまたいで対象を広げて再提起される（`is_file` → `is_dir`，再展開 → バリアント切替）．
1 件直すときに同種の箇所を横断して直すと巡数を減らせる．

## 🧰 新規リポジトリ立ち上げの詰まりどころ

- `gh repo create` 直後のリポジトリでは，Actions タブで有効化するまでワークフローが一切走らなかった．
  `actions/permissions` API は `enabled: true` を返し，ワークフローも `active` と表示される．
  そのため API からは区別できない．
  唯一の兆候は head コミットの check-suite に `github-actions` が現れないことだった．
  有効化後は PR の close / reopen で `pull_request` を再発火できる．
- `pip install --user pipx` は `%APPDATA%\Python\Python313\Scripts` に入り，PATH に無い．
  `py -m pipx ensurepath` で PATH へ追加し，シェルを開き直す．
  開き直す前のシェルでは `py -m pipx ...` と書けば動く．
- Private リポジトリからの `pipx install git+https://...` は，追加設定なしで入った．
  ローカルの Git 認証が通っていれば足りる．

## 🤖 サブエージェント運用の学び

- サブエージェントがバックグラウンドで始めた 3 GB の取得は，エージェント終了と同時に止まった．
  長時間処理はメイン側で `run_in_background` により実行し，完了通知を待つ．
- 監視対象の run を「ブランチの最新 2 件」で取ると，返信コメントで発火した別ワークフローを拾った．
  PR のチェック全体を待つなら `gh pr checks --watch` を使う．
- 実装は `implementer` へ委譲し，レビュー指摘ごとに「テスト先行・触ってよい範囲・期待出力」を明記した．
  3 巡とも委譲 1 回で収束し，メイン側は判断と返信に集中できた．
